The builder UI is one client of the builder engine. Other modules, such as the [AI assistant](/docs/modules/ai/introduction) or your own tooling, drive the same operations through the interface or the HTTP API.

## The interface

[`@antelopejs/interface-dms-builder`](https://github.com/AntelopeJS/dms-builder/tree/main/packages/interface-dms-builder/docs) exposes every operation as an `InterfaceFunction`. A module in the same process imports an operation and calls it like any async function.

```ts [src/seed-page.ts]
import { AddBlock } from "@antelopejs/interface-dms-builder";

const result = await AddBlock({
  page: "/revenue",
  name: "total",
  type: "KpiCard",
  config: { title: "Total revenue", icon: "i-ph-currency-eur" },
});
if (result.ok) {
  console.log(result.data.path); // "/revenue#total"
}
```

A mutation returns an `OpResult`. On success it is `{ ok: true, data, changes }`, where `changes` lists the files the operation changed, with optional `warnings`. On failure it is `{ ok: false, error }`. The interface reference covers these topics:

## The HTTP API

Every route sits under `/api/builder` and requires an authenticated tenant owner. A route that runs a mutation, or a read that can fail, answers with the interface's `OpResult`, so a client branches on `ok` rather than on the status code. The list reads (`GET /catalog`, `GET /pages`, `GET /categories`, `GET /resources`, `/query-templates` and `/data-sources`) and the reads that describe the project (`/status`, `/tables/usage`, `/page/impact`, `/page/access` and `/permissions`) answer with their value. `/page/impact` and `/page/access` answer `404` with `{ code: "not_found", ref }` for an unknown page.

| Method | Path | Body or query | Operation |
| --- | --- | --- | --- |
| `GET` | `/status` | | `{ ok: true, projectRoot }`, the project root the builder edits |
| `GET` | `/catalog` | | `GetCatalog` |
| `GET`, `POST` | `/pages` | `CreatePageInput` | `ListPages`, `CreatePage` |
| `GET`, `POST` | `/categories` | `CreateCategoryInput` | `ListCategories`, `CreateCategory` |
| `PUT`, `DELETE` | `/category` | `{ category, patch }`, `?ref=` | `ConfigureCategory`, `DeleteCategory` |
| `GET`, `DELETE` | `/page` | `?ref=` | `GetPageStructure`, `DeletePage` |
| `POST` | `/page/configure` | `{ page, patch, expectedVersion? }` | `ConfigurePage` |
| `POST` | `/page/preview` | `{ page, draft }` | `PreviewLayout` |
| `POST` | `/page/blocks` | `{ page, draft, expectedVersion? }` | `SetPageBlocks` |
| `GET` | `/page/impact` | `?ref=` | What deleting the page takes with it |
| `GET` | `/page/access` | `?ref=&permission=` | Who reaches the page and each of its blocks |
| `GET` | `/permissions` | | The permissions the DMS registered |
| `GET`, `POST` | `/resources` | `CreateResourceInput` | `ListResources`, `CreateResource` |
| `GET` | `/resource` | `?ref=` | `GetResourceStructure` |
| `POST` | `/resource/configure` | `{ resource, patch, expectedVersion? }` | `ConfigureResource`, the routes a table serves |
| `POST`, `PUT`, `DELETE` | `/resource/fields` | `{ resource, field, expectedVersion? }`, `{ path, patch, expectedVersion? }`, `?path=` | `AddField`, `ConfigureField`, `RemoveField` |
| `GET` | `/tables/usage` | | `{ readers, rows }`, the pages reading each table and its rows in the request's tenant |
| `GET` | `/query-templates` | | `ListQueryTemplates` |
| `GET` | `/data-sources` | `?responseKind=` | `ListDataSources` |
| `POST`, `PUT`, `DELETE` | `/queries` | `{ page, input, expectedVersion? }`, `{ query, patch, expectedVersion? }`, `?ref=` | `AddQuery`, `ConfigureQuery`, `RemoveQuery` |
| `POST` | `/query-preview` | `{ query, args? }` | `PreviewQuery` |
| `GET` | `/query-preview` | `?query=<JSON>` and the route's own parameters | The answer the saved query's route would serve |
| `POST` | `/refresh` | | `RefreshSourceIndex`, then `{ ok: true }` |

In a `/page/configure` or `/category` patch, an option sent as `null` is removed from the file.

Both query previews read the tenant from the request, never from the body. `GET /query-preview` answers with the bare body the route will serve once saved. If it cannot run the query, it answers `400` for a malformed request, `404` for `not_found` and `422` for any other error.

### Database workspace routes

These routes serve the **Database** workspace of the builder. Rows of an external database reach the owner through `/database/sample` only. No interface function of the builder returns them.

| Method | Path | Body or query | Answer |
| --- | --- | --- | --- |
| `GET` | `/database/connections` | | Each catalog connection, with `id` and what its provider reports (`engine`, `version`, `database`, `role`) or an `error` |
| `POST` | `/database/analyse` | `AnalyseDatabaseInput` | `AnalyseDatabase` |
| `GET` | `/database/analysis` | `?id=` or `?connection=` | `GetAnalysis`, or the latest analysis of the connection. `404` when the connection has none. |
| `POST` | `/database/map` | `MapResourcesInput` | `MapResources` |
| `GET` | `/database/mapping` | `?connection=&module=` | `GetMapping` |
| `GET` | `/database/project` | | `{ modules, databasePin? }` |
| `POST` | `/database/project` | `{ steps, opts?, variables? }` | `ConfigureProject`. With `variables`, the builder first writes their development values into `.env`. |
| `GET` | `/database/connection` | `?connection=` | `{ wiring, details }`. `404` for an unknown connection. |
| `POST` | `/database/connection/remove` | `{ connection, dryRun? }` | An `OpResult` of the configuration change |
| `POST` | `/database/connection/url` | `{ connection, url }` | An `OpResult` with the `variable` it set. A URL without a password keeps the current one. |
| `POST` | `/database/sample` | `{ connection, relation, columns, limit }` | The sampled rows. `404` for an unknown connection. |

A route that refuses the request answers `422` with `{ code: "refused", message }`.

### Edit a whole page

An editor holds a draft and writes it once, rather than replaying each edit. It uses three routes in this order:

1. `GET /api/builder/page?ref=/dashboard` returns the `PageStructure`, with its `version`.
2. `POST /api/builder/page/preview` returns the serialized layout of the draft. The editor calls it as often as it needs.
3. `POST /api/builder/page/blocks` with `expectedVersion` writes the draft in one transaction and one typecheck. If the page changed since the read, it fails with `stale` instead of overwriting it.

Every write also fails with `stale`, with or without `expectedVersion`, when a file it edits changes on disk while the write runs. Nothing is written. Read the page again and retry.

## Make your blocks editable

The builder reads blocks back by their shape. A hand-written declaration that matches the grammar of a DMS factory call is as editable as a generated one. A declaration that departs from that grammar shows as opaque, and the builder does not rewrite it.

A factory imported from its documented subpath (`@antelopejs/interface-dms/base/kpi-card`) reads exactly like one imported from the `base` barrel. A component the catalog has no factory for, such as one a helper of your own returns, shows as an opaque block, and the builder keeps it as written when it saves the page.

A block type declared with `RegisterBlockType` appears in the catalog. The catalog takes its label, icon and description from the definition's `meta`, and generates its settings panel from its `schema`. A block's `.meta({ name, description, icon })` names the permission the DMS registers for it, which is how the role editor shows it.

## Frontend module

The backend registers the builder's frontend module at priority 100, and only when the builder is on. The backend's manifest entry then carries `dmsBuilder.enabled === true`. `frontend-vue/dms.frontend.ts` checks that option before it registers the `DmsBuilder` components and the client plugin.

### Languages

The builder's texts ship in `frontend-vue/i18n/locales/builder-en-GB.json` and `builder-fr-FR.json`, under the `dms_builder` namespace. The DMS frontend loader merges them into the app's catalog like the texts of any module. The header button's label is the key `$dms_builder.action.edit_page`, which the DMS header translates for its tooltip and its aria-label. English is the fallback locale, so a language the module does not ship reads in English. An app can override any text by declaring the same key in its own locale files.

The locale files cover the header button, the editor bar, the banners over the page and the toasts. The panels are in English only.

The app's own display strings read the same way. A page title, a category name or a block heading written as a `$` key (`$demo.nav.home`) shows in the reader's language wherever the editor draws it. That covers the bar, the canvas header, the layers, the pages tree and the inspector's heading. The fields that edit the string keep the key, so saving writes the key back.
