# External Databases

## Overview

A DMS project can show pages over a database it does not own: a client's PostgreSQL, MongoDB or RethinkDB, read and written live through that engine's module (`@antelopejs/postgres`, `@antelopejs/mongodb`, `@antelopejs/rethinkdb`) in external mode. The builder takes such a database in four moves, each an operation:

1. **Wire it** into `antelope.config.ts` with `ConfigureProject`: the provider module, a local module for its tables, the builder's catalog connection, and the DMS module's pin to the project's own database.
2. **Analyse it** with `AnalyseDatabase`, which reads the catalog and proposes a mapping by fixed rules. It writes nothing.
3. **Decide** the proposal: a person in the builder's *Database* workspace, or an assistant through these operations.
4. **Map it** with `MapResources`, which writes table classes, controllers and TableView pages into the module bound to the database.

The builder reaches the database through `@antelopejs/interface-database-catalog`, a connection declared on its own module entry. It never connects with credentials of its own.

## Wire the Project

`ConfigureProject(steps, opts?)` applies its steps to `antelope.config.ts` as one edit. Every step is validated before anything is written, and a refused step writes nothing. With `{ dryRun: true }` it answers the changes it would make, as `OpResult.changes`, so a caller can show the diff before writing.

| Step | Writes |
| --- | --- |
| `AddModule` | a module entry, refusing an id that exists |
| `ConfigureModule` | merges config, `importOverrides` (pins and connection ids), `exportPriority`, `disabledExports` and env variable names into an entry |
| `CreateLocalModule` | scaffolds a local module and adds its entry; with `connection`, its record names that connection |
| `RemoveModule` | removes an entry and the `envOverrides` entries supplying its config, refusing one another module still reads through; its files stay |
| `RemoveConnection` | removes a named connection to an interface from every module's `importOverrides` |

`env` takes variable names, never values: each is added to `envOverrides`, and to `.env.example` when the project has one.

The provider's entry depends on its engine:

| Engine | Package | `env` | `disabledExports` |
| --- | --- | --- | --- |
| PostgreSQL | `@antelopejs/postgres` | `url` | none |
| MongoDB | `@antelopejs/mongodb` | `url` and `database` | `@antelopejs/interface-mongodb` |
| RethinkDB | `@antelopejs/rethinkdb` | `url`, the database as its path | `@antelopejs/interface-rethinkdb` |

`disabledExports` keeps core from ever offering the external instance's raw client, so a module that needs the DMS's own MongoDB or RethinkDB client never gets the client's database instead.

```typescript
import { ConfigureProject } from "@antelopejs/interface-dms-builder";

const catalog = "@antelopejs/interface-database-catalog";

const result = await ConfigureProject([
  {
    op: "AddModule",
    id: "postgres-erp",
    entry: {
      source: { type: "package", package: "@antelopejs/postgres", version: "^0.2.0" },
      config: { mode: "external", statementTimeoutMs: 30000 },
      env: { url: "ERP_DATABASE_URL" },
      exportPriority: { "@antelopejs/interface-database": -1 },
    },
  },
  {
    op: "CreateLocalModule",
    id: "erp-tables",
    path: "modules/erp-tables",
    connection: "erp",
    entry: {
      importOverrides: [{ interface: "@antelopejs/interface-database", source: "postgres-erp" }],
    },
  },
  {
    op: "ConfigureModule",
    id: "dms",
    entry: { importOverrides: [{ interface: "@antelopejs/interface-database", source: "mongodb" }] },
  },
  {
    op: "ConfigureModule",
    id: "dms-builder",
    entry: { importOverrides: [{ interface: catalog, source: "postgres-erp", id: "erp" }] },
  },
]);
```

- The provider's `exportPriority` of `-1` keeps the project's own database the default for every module that does not pin `interface-database`.
- The tables module pins `interface-database` to the provider, and uses the DMS. Core passes that pin on to the DMS, which every other module reaches with the default, so the DMS pins the project's own database to settle it. A DMS that already pins `interface-database` needs nothing more.

The connection exists once the project restarts with the variable set.

### Remove a Connection

Removing a connection takes its catalog connections and its tables module out of the configuration, with `RemoveConnection` and `RemoveModule`. The tables module's folder is deleted with it. The database itself is untouched.

The tables module is the one whose `dmsBuilder.database` record names the connection, which `CreateLocalModule` writes with `connection` (the single-step `CreateLocalModule` takes it in its options). Another module that reads through the provider is never removed or deleted.

The provider goes too, with the variables that supply its configuration in `envOverrides`, `.env` and `.env.example`, only when it was added for this connection alone: its `exportPriority` for `@antelopejs/interface-database` is below the project's own database, and no module or connection the removal leaves names it. Otherwise it stays, since it may be the project's own database.

A removal is all or nothing: the folders are moved aside and `.env` is edited first, and both are put back when the configuration cannot be written.

## Analyse a Database

`AnalyseDatabase({ connection, module, schemas? })` starts a job and answers it at once: profiling a database takes a while. `GetAnalysis(id)` answers the job's `progress` while it runs, then its `proposal`, or its `error`.

```typescript
import { AnalyseDatabase, GetAnalysis } from "@antelopejs/interface-dms-builder";

const started = await AnalyseDatabase({ connection: "erp", module: "erp-tables" });
if (started.ok) {
  const state = await GetAnalysis(started.data.id);
  // state.data.status: "running" | "done" | "failed"
}
```

- One job runs per connection. Starting another while one runs answers the running one.
- A finished job is kept until the next one on its connection, or a restart.
- Relations the module has mapped, or recorded as excluded, are not proposed again.
- Above 200 relations to profile, the proposal holds a single `schemas` question instead, and the analysis runs again with `schemas`.

## Read a Proposal

A `MappingProposal` is a `MapResources` input in which every choice says where it came from:

```typescript
interface Proposed<T> {
  value: T;
  rule: string;            // "R6", "L1", "F5"…
  kind: "fact" | "default";
}
```

A **fact** follows from the catalog with no judgement. A **default** is a judgement to check.

| Rule | When | Then |
| --- | --- | --- |
| R1 | the catalog says unmappable | excluded, with its reason |
| R2 | no key | stats only: table class and model, no page |
| R3 | no rows | excluded |
| R4 | a framework's or a migration tool's table | excluded |
| R5 | keyed by its two references | stats only |
| R6 | keyed, with rows and a label | TableView |
| R7 | keyed, no label, referenced | TableView labelled by its key, and a `label` question |
| R8 | keyed, no label, not referenced, with a time axis | stats only |
| R9 | anything else | a `purpose` question, nothing proposed |
| L1, L2 | the label by name, then by order; titles from short comments, else from names | |
| F1–F5 | columns no type reads and secrets left out; the first declaration; references the database declares, and references found whole, as relation columns | |
| D1 | a `string` column the profile calls enum-like, of 2 to 10 categories that cover every non-null row | `display`: a badge, one toned item per value, by rows |
| D2 | a `number` column whose name ends in `total`, `amount`, `price`, `cost`, `revenue` or `subtotal` | `display`: a price |
| D3 | a relation column the database did not comment | `label`: the target's title in singular, "Customer" not "Customer id"; `MapResources` takes it too when a field leaves `label` out |
| T1 | of the filterable badge columns of 2 to 6 values, the first named like `status`, `state`, `stage` or `type`, else the one with the fewest values | `tabs` on the resource |
| W1 | every TableView | read-only |

A badge's tones come from the value: `paid`, `active`, `done`, `completed`, `shipped`, `delivered` and `approved` are `success`; `pending`, `draft`, `processing`, `waiting` and `review` are `warning`; `failed`, `cancelled`, `canceled`, `refunded`, `rejected`, `error` and `blocked` are `error`; `new` and `open` are `info`. Other values take `primary`, `secondary`, `info` and `neutral` in turn. A price uses the DataType's default currency.

Each field also carries the declarations its column `accepts`, and its profile's aggregates: traits, nulls, distinct values, range and categories. Never a row.

Each resource also carries its `rows`, counted by the profile or estimated, when either is known.

What the rules could not decide is in `open`, each item with its options and what the proposal holds meanwhile:

- A `label` item offers every column a field reads, the key among them.
- A `reference` item offers a plain column, the target its values were found in, and every TableView whose single-column key accepts the column.
- A `purpose` item carries the `resource` it would map, should the answer be to map it, and in its own `open` the questions that resource leaves: they are asked only once the answer maps it.
- A `field-type` item asks which declaration reads a field of several native types.

A document database declares no field types, so its catalog reads them from a sample. When no type covers enough of a field's values (`int 60% | string 40%`), the field is left out and a `field-type` item asks which declaration reads it: its options are a declaration per type seen, and leaving it out. The `_id` of a collection without a key is never declared, so it is left out and asks nothing. `MapResources` accepts the declaration it answers. MongoDB and RethinkDB declare no references either, so F5 finds them all.

## Map Relations

`MapResources(input)` reads the descriptions of the relations through the builder's connection, checks every choice against them, and writes in one typechecked transaction. Then it creates the connection's category `pages.<connection>` and the TableView pages.

```typescript
import { MapResources } from "@antelopejs/interface-dms-builder";

const result = await MapResources({
  module: "erp-tables",
  connection: "erp",
  resources: [
    {
      relation: "erp.customers",
      label: "name",
      title: "Customers",
      tableView: true,
      writable: false,
      fields: [{ column: "name", searchable: true }, { column: "segment", filterable: true }],
    },
  ],
  excluded: [{ relation: "erp.schema_migrations", reason: "a framework's or a migration tool's table" }],
});
```

- **Names are the database's own.** `_id` is declared only where the relation has a key, and nothing creates or alters a table. A MongoDB collection's key is `_id` itself, which is declared once.
- **Relation columns** point at a relation of the batch, or one the module mapped before, by its single-column key.
- **A relation column's `label`** is written as sent. Left out, it keeps the label its controller holds if its relation was mapped before and held the column; otherwise it takes D3, the title of the relation it points at in singular ("Customer", not "Customer id"), as the target is titled by this call, by its page if it was mapped before, else by its name humanized. A column the database commented with a short first sentence takes that sentence instead (L2). A column that is not a relation column takes its name, humanized. A call that never sends a `label` therefore gets the analysis's labels on a first mapping and loses nothing on a remap.
- **A column's `display`** is `{ kind: "badge", items: [{ value, label, tone }] }` on a `string` column, or `{ kind: "price" }` on a `number` one. A relation column takes none. Left out, the column keeps the display it has if its relation was mapped before, read back from its controller as `GetMapping` reads it; if the relation is new, it takes the display D1 or D2 proposes. `null` writes the column plain, over any display it had. A call that never sends a `display` therefore gets the proposal on a first mapping and loses nothing on a remap.
- **Where a proposal comes from.** `MapResources` reads the profile of a new relation through the catalog connection at map time, since D1 needs it. When the profile cannot be read, it takes the proposal from the connection's last `AnalyseDatabase`; when there is none either, D2 still applies by the column's name, no column becomes a badge, and the result warns `display_not_proposed`. A display that does not suit the column's declaration, such as a badge on a column declared `number`, is dropped when it was kept or proposed, and refused only when sent.
- **A TableView's `tabs`**: `tabs: { column }` writes "All" and a tab per value of that column's badge to the TableView, over the `tabs` it holds; the column must be filterable and drawn as a badge. Left out, a page already mapped keeps its tabs, and a new relation takes the tabs T1 proposes among its filterable badge columns: a column left unfilterable is not tabbed. `null` writes none: it adds no tabs to a new relation, and removes from a page already mapped the tabs a mapping wrote from a badge, as `display: null` removes the badge. Tabs edited by hand are kept.
- **Mapping again** a relation already mapped rewrites it from the new choices. Its page is created, kept or removed as `tableView` says, and takes the new `title`. The module's relation columns pointing at it take its new `label`.
- **The module's `package.json`** records the connection and the `excluded` tables with their reasons, so the next analysis does not propose those tables. Mapping one later removes it from the record:

  ```json
  "dmsBuilder": {
    "database": {
      "connection": "erp",
      "excludedTables": { "erp.schema_migrations": "a framework's or a migration tool's table" }
    }
  }
  ```
- **In a mapped module**, `CreateResource` and `AddField` are refused, since its tables are the database's. `DeleteResource` keeps the client's rows and warns `data_kept`.
